## Design Patterns

### Pattern: iOS-Native Progressive Web App
**Problem**: Web apps need to feel native on iOS devices while maintaining web accessibility
**Solution**: CSS environment variables with progressive enhancement
**When to use**: Mobile-first PWAs targeting iOS users

```css
/* Comprehensive iOS PWA implementation */
@supports (padding: max(0px)) {
  .app-container {
    padding-top: env(safe-area-inset-top);
    padding-left: env(safe-area-inset-left);
    padding-right: env(safe-area-inset-right);
    padding-bottom: env(safe-area-inset-bottom);
  }
}

/* Dark mode date picker support */
input[type="date"], input[type="time"] {
  color-scheme: dark light;
}
```

**Accessibility Notes**:
- Safe area insets don't affect screen reader navigation
- Color scheme changes apply to system controls
- Maintain focus indicators within safe areas

### Pattern: Accessible Chart Implementation with Data Table Alternative
**Problem**: Complex visualizations need to be accessible to screen readers
**Solution**: ARIA labels with data table alternatives
**When to use**: Any data visualization component

```svelte

>
  <div
    role="img"
    aria-label="Chart displaying {workoutCount} workouts from {startDate} to {endDate}"
    bind:this={chartContainer}
  >
    <!-- D3 chart content -->
  </div>
  
  <!-- Required data table alternative -->
  <details class="mt-4">

      <Table.Header>
        <Table.Row>
          <Table.Head>Date</Table.Head>

```

## Usability Guidelines

### Touch Target Implementation
- **Do**: Ensure minimum 44px × 44px touch targets for all interactive elements
- **Do**: Use `min-h-[44px] min-w-[44px]` classes for critical buttons
- **Don't**: Assume small visual elements are acceptable if they're touch targets
- **Consider**: Adding invisible padding to extend touch areas when needed

### Mobile Gesture Handling
- **Do**: Provide keyboard alternatives for touch gestures
- **Do**: Test gesture conflicts with browser navigation
- **Don't**: Rely solely on touch interactions for core functionality
- **Consider**: Haptic feedback for enhanced native feel

### Component Accessibility
- **Do**: Include data table alternatives for all charts
- **Do**: Use proper ARIA live regions for dynamic content
- **Don't**: Rely on color alone to convey information
- **Consider**: Automated accessibility testing in development workflow

### Accessible Form Error Handling
```svelte
<!-- Enhanced form validation with ARIA -->
<script>
  let errors = {};
  let touched = {};
  
  function announceError(field, message) {
    // Announce error to screen readers
    const errorId = `${field}-error`;
    const errorElement = document.getElementById(errorId);
    if (errorElement) {
      errorElement.textContent = message;
      // Trigger screen reader announcement
      errorElement.setAttribute('aria-live', 'assertive');
      setTimeout(() => {
        errorElement.setAttribute('aria-live', 'polite');
      }, 100);
    }
  }
</script>

<!-- Form field with complete accessibility -->
<div class="grid gap-2">
  <Label for="workout-duration">Duration (minutes) *</Label>
  <Input 
    type="number" 
    id="workout-duration"
    bind:value={duration}
    min="1"
    max="300"
    inputmode="numeric"
    pattern="[0-9]*"
    class="min-h-[44px] text-lg"
    aria-describedby="duration-help {errors.duration ? 'duration-error' : ''}"
    aria-invalid={errors.duration ? 'true' : 'false'}
    aria-required="true"
    on:blur={() => touched.duration = true}
  />
  
  <div id="duration-help" class="text-sm text-muted-foreground">
    Enter workout duration between 1 and 300 minutes
  </div>
  
  {#if errors.duration && touched.duration}
    <div 
      id="duration-error" 
      class="text-sm text-destructive" 
      role="alert"
      aria-live="polite"
    >
      {errors.duration}
    </div>
  {/if}
</div>
```

    }
  }
